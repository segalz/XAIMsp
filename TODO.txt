Closed: Grok answers arrive truncated
-------------------------------------

Reported, reproduced, diagnosed and handled 2026-09-07.

WHAT WAS HAPPENING

Two ways a run ends early, treated differently by the bridge:

1. The turn budget is exhausted. grok exits 1 with `Error: max turns reached`,
   and a non-zero return code already raised. This case was honest.

2. The CLI stops itself. grok exits 0 with `"stopReason": "cancelled"`. Only
   `proc.returncode` was inspected, so this read as success. grok's `text`
   accumulates narration across turns, so what came back was narration -- "I'll
   read the files, then count them" -- presented as the answer.

WHY IT CANCELLED

xAI's documentation lists `end.stopReason` as one of `end_turn`, `max_tokens`,
`max_turn_requests`, `refusal`, `cancelled`, and says a turn ends early on
interrupt, permission rejection, or the turn limit.

In headless mode the usual cause is permission. There is nobody to approve a
tool call. Proven by experiment rather than inferred:

    task: create a file, then read it back
    no permission mode    stopReason=cancelled  turns=1  file created: No
    permission_mode=auto  stopReason=end_turn   turns=3  file created: Yes

Read-only work was never gated -- `read_file`, `grep`, `list_dir` and even
`git log --oneline` all completed either way. Only the write tripped it. The
turn budget was ruled out separately: a cancel occurred on a run where
`--max-turns` was not sent at all.

The bridge's own log offered nothing: all 30 `handle_prompt.done` entries say
`ok: true`, including the cancelled runs, and the CLI never logs a turn limit.

WHAT CHANGED

- A reply whose `stopReason` is not `end_turn` arrives behind a line saying so,
  with the partial text kept underneath, and the line names the likely cause.
- Approval is granted by default, which is what stops the cancels. This is a
  real grant: Grok can write files and run commands in the workspace without
  asking. It was requested deliberately after the trade-off was put plainly.
- `permission_mode="readOnly"` withholds that approval for a single call, so
  the CLI's gate stands, and appends a rule telling Grok the request is
  read-only so it does not spend turns on tools that would be refused. The gate
  is the boundary; the rule only saves effort. The default is unchanged.
- `grok_code_review` moved off `--output-format plain`, which carries no
  stopReason. A cancelled review used to come back as "no additional
  high-confidence findings" -- the exact phrase for a clean one.
- A timeout keeps the partial stdout that `TimeoutExpired` carries.

Note for anyone reading an older copy of this file: the turn-limit reason is
`max_turn_requests`. There is no `max_turns` stopReason; that was a guess.


Closed: calls no longer queue behind one another
-----------------------------------------------

`_GROK_LOCK` serialised every invocation. It arrived with the first commit and
recorded no reason, and the thing it was guarding turns out not to need it:
grok sessions are independent processes, xAI ships an "agent swarm" that runs
several on purpose, and a concurrent-auth-refresh bug that did exist was fixed
before the version installed here (1.0.13).

Measured before changing anything: four concurrent calls, four correct and
uncrossed answers, 10.4s wall against 24.8s serialised.

Replaced with a bounded semaphore of 4 rather than removed outright. Each grok
is a ~166MB process and they all draw on one account pool, so the risk worth
guarding is a burst, not overlap. Callers past the bound wait for a slot.


Closed: the turn ceiling is pinned
----------------------------------

`--max-turns` used to be sent only when a caller supplied one, leaving whatever
ceiling the CLI happened to ship that release. grok documents no default and
`--help` states none, so it was unknown and free to change under us.

Every call now sends `DEFAULT_MAX_TURNS` (50) unless the caller passes its own,
and a caller who needs more simply passes more. 50 is far above real work --
the heaviest task measured against this bridge finished in 5 turns -- so it does
not constrain an honest run. What it stops is a stuck loop quietly spending
quota.

Note `num_turns` is documented as the same counter family as `--max-turns` but
"not a guarantee of exact equality when rounds lack usage or hit gates", so the
two will not always agree exactly.
