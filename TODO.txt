Open: Grok answers arrive truncated -- diagnosed, not yet fixed
--------------------------------------------------------------

Reported 2026-09-07, reproduced the same day. The earlier guesses in this file
were wrong and are corrected below.

WHAT ACTUALLY HAPPENS

There are two ways a run ends early, and the bridge treats them very
differently:

1. The turn budget is exhausted.
   grok exits 1 with `Error: max turns reached` on stderr. `_run_grok` raises
   on a non-zero return code, so the caller sees a loud failure. This case is
   already honest -- nothing to fix.

2. The CLI stops itself early.
   grok exits 0 with `"stopReason": "cancelled"` and a `num_turns` BELOW the
   budget it was given. `_run_grok` only inspects `proc.returncode`, so it
   treats this as success, extracts the accumulated text, and hands it back.

Case 2 is the defect. grok's `text` field accumulates narration across turns,
so when a run ends before the work is done, `text` holds the narration alone --
"I'll read the files, then count them" -- with no answer in it. The caller
receives that as a finished reply.

REPRODUCTION (2026-09-07, grok 1.0.13, model grok-4.6)

Prompt: audit every file under tests/, count test functions per file, rank them.
Workspace: C:\Develop\traidAi.

    max_turns=1   RuntimeError "grok exited 1"          <- visible
    max_turns=4   RuntimeError "grok exited 1"          <- visible
    max_turns=8   returncode 0, stopReason "cancelled", <- SILENT
                  num_turns 4, text 435 chars of pure
                  narration ending "...so I'll count
                  `def test_` in each file to finish
                  the ranking."

Note stopReason is "cancelled", not "max_turns". A field named max_turns does
not appear at all; the earlier note in this file guessed wrong.

This is not hypothetical: it hit the F5 review in the traidAi work on the same
day. A decision request came back as four narration fragments with no decision,
no error, and no indication anything was missing.

THE FIX

`_run_grok` should stop treating a clean exit as a complete answer. A
`stopReason` other than `end_turn` means the reply is partial, and the caller
must be told -- raising is the safest default, since a partial analysis that
looks complete is what makes this dangerous rather than merely annoying.

`_result_payload` drops everything except `result["text"]` when raw_output is
false, so today `stopReason` cannot reach a normal caller even if they wanted
to check it themselves.

Whatever shape the fix takes, the test for it must assert on a payload carrying
stopReason "cancelled" with returncode 0. That combination is the whole bug.
