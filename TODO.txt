Closed: Grok answers arrive truncated
-------------------------------------

Reported, reproduced and handled 2026-09-07.

There are two ways a run ends early, and the bridge treated them differently:

1. The turn budget is exhausted. grok exits 1 with `Error: max turns reached`,
   and a non-zero return code already raised. This case was honest.

2. The CLI stops itself. grok exits 0 with `"stopReason": "cancelled"` and a
   `num_turns` BELOW the budget it was given. Only `proc.returncode` was
   inspected, so this read as success.

Case 2 was the defect. grok's `text` accumulates narration across turns, so a
run that ends before the work is done leaves narration alone -- "I'll read the
files, then count them" -- and that was handed back as the answer. Which of the
two happens is not deterministic: the same prompt and budget produced each on
different runs.

A reply whose `stopReason` is not `end_turn` now arrives behind a line saying
so, with the partial text kept underneath. Raw payloads carry `stop_reason` and
`incomplete`.

Note for anyone reading the old version of this file: the stopReason is
"cancelled". There is no "max_turns" value; that was a guess and it was wrong.

`grok_code_review` was the dangerous case. It ran on `--output-format plain`,
which carries no stopReason at all, so the guard could not see it. Worse, a
cancelled review came back as "no additional high-confidence findings" -- the
exact phrase for a clean review. Silence that reads as approval is the worst
failure a review tool can have. It now uses JSON like everything else, and its
preamble trim is skipped on an incomplete reply so it cannot eat the warning.

A timeout used to raise a bare "grok timed out after Ns", discarding the
partial stdout that `TimeoutExpired` carries -- the only evidence of how far it
got. Both streams are now included in the error.


Open: why does grok cancel itself?
----------------------------------

The reporting is fixed; the cause is not. grok stops mid-work, exits 0, and
says "cancelled", well inside the turn budget. It is not deterministic. It may
be a failed tool call inside grok or a loop guard. Runs are still lost -- they
are merely visible now. This is the next real question, and the hardest.


Open: the bridge is single-file-through
---------------------------------------

`_GROK_LOCK` serialises every invocation. Any attempt to fan work out into
parallel grok calls will queue behind it and gain nothing. Worth knowing before
anyone designs a swarm on top of this bridge.


Open: no default max_turns
--------------------------

`--max-turns` is sent only when a caller supplies it, so the CLI's own default
applies -- unknown, unpinned, and free to change on upgrade. Pinning a sane
default would make behaviour reproducible.
